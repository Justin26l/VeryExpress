# v0.10.0

## Tenant isolation

A document can be scoped to a tenant. The feature is off by default: set `vex.config.tenant.enable`
and the generator emits the tenant module. With it off, no tenant file is written and
`Authentication.middleware` / `JWTService` contain no tenant code.

```jsonc
// vex.config.json
"tenant": {
    "enable": true,
    "IsolationMode": "option"     // "preSelect" | "option"; defaults to "preSelect"
}
```

```jsonc
// a document schema
"x-documentConfig": {
    "documentName": "Project",
    "isolation": [
        { "field": "tenantId", "source": "user.tenantId", "onMissing": "deny" }
    ]
}
```

The tenant id is a UUID. The header (`x-tenant-id`) and the token claim (`tenantId`) are fixed;
there is no custom header or claim name.

### `preSelect` — one app build per tenant

1. Every request must carry `x-tenant-id`; missing or non-UUID → `400`.
2. The header is the tenant; a token claim is ignored.
3. Login and refresh verify the `UserTenant` mapping; not a member → `403`.
4. Registration links the new account to the header tenant.

### `option` — log in, then choose an organization

1. Login and registration need no tenant. Tokens are minted without a claim.
2. `GET /api/tenant` lists the user's tenants.
3. `POST /api/tenant/select` `{ tenantId }` validates the mapping (`403` if absent) and returns new
   access + refresh tokens carrying `tenantId`.
4. Protected requests check the claim: missing → `401` (`tenant not selected`), malformed → `401`.
5. A request with no token is a guest; a valid header may identify the tenant for public endpoints.
6. Refresh keeps the claim and re-validates the mapping.

### `UserTenant`

The module owns the mapping table. It is copied into `jsonSchemaDir` on first enable and left alone
afterwards, so the app can extend it. `(userId, tenantId)` is unique; both are UUID columns and no
REST controller is generated.

```ts
// TenantService.gen.ts
addUserTenant(tenantId)              // userId from UserContext; idempotent
linkUserTenant(userId, tenantId)     // registration / provisioning
hasUserTenant(userId, tenantId)
removeUserTenant(userId, tenantId)
listUserTenants(userId?)
```

The app decides where tenant ids come from; it only calls `addUserTenant` or `linkUserTenant`.

## Account deletion

`auth.deleteAccount` accepts a boolean or an object:

```jsonc
"auth": {
    "deleteAccount": {
        "enabled": true,
        "deleteTables": ["UserContact", "UserAddress"]
    }
}
```

- `deleteTables` rows are removed with the account in **both** modes. The generator resolves the
  link field per document (`x-foreignKey` to the identity document, else `userId`) and fails
  generation when a table cannot be linked.
- A document with `x-vexData: "softDelete"` is soft-deleted row by row; the rest are hard-deleted.
- With tenant isolation enabled, deletion removes the `UserTenant` mapping instead of tombstoning
  the `User`: the account can keep working in its other tenants. `UserContext.tenantId` is required
  (`400`), and the mapping must exist (`404`).
- `deleteAccountResponse` gains `tenantId`, `related` (rows per cleaned table) and
  `deleted.userTenants`.

## Isolation rules replace the single ownership field

`x-documentConfig.isolation` is a list. Each rule is `{ field, source, onMissing }`:

| Key | Values |
| --- | --- |
| `field` | a `string` property of the document |
| `source` | `user._id` \| `user.tenantId` |
| `onMissing` | `skip` \| `deny` (default: `skip` for `user._id`, `deny` for `user.tenantId`) |

The legacy `dataIsolation: { field }` form keeps working and is normalized to
`{ field, source: "user._id", onMissing: "skip" }`.

Behaviour changes that follow:

- **Isolation fields are no longer accepted in request bodies.** They are omitted from the generated
  `Payload{Document}` type, and tsoa answers `400` to a request that sends one.
- **Updates strip isolation fields.** A row cannot be moved to another owner or tenant through
  `PATCH` / `PUT`.
- **`onMissing: "deny"` fails closed.** A document that declares a tenant rule answers `403` when
  the request carries no tenant.
- **Both adapters apply isolation** to every read and write path.

## `UserContext` layers instead of replacing

`UserContext.run(patch, fn)` merges the patch onto the store of the enclosing scope, so the L0 tenant
pass, authentication and the post-auth tenant pass do not erase each other. The store carries
`tokenData`, `requestedTenantId` and `tenantId`.

## Generated files

| File | When |
| --- | --- |
| `jsonSchema/UserTenant.json` | `tenant.enable`, if absent |
| `_middlewares/TenantScopeContext.gen.ts` | `tenant.enable` |
| `_middlewares/TenantScope.gen.ts` | `tenant.enable` |
| `_services/TenantService.gen.ts` | `tenant.enable` |
| `_controllers/TenantController.gen.ts` | `option` mode |
| `_types/Tenant.gen.ts` | `option` mode |
| `_middlewares/DataIsolationRegistry.gen.ts` | always — entity → rule list (empty when no rules) |

Turning the feature off removes the tenant files on the next run.

## Migration

1. Re-run the generator.
2. `tenant` config from an earlier draft (`resolve`, `claim`, `bypassRoles`, `membership`,
   `userField`) is rejected with a message: replace it with `{ enable, IsolationMode }`.
3. Existing `dataIsolation` schemas need no edit. To scope by tenant, add the `tenant` config and a
   `user.tenantId` rule.
4. Add a tenant column (and a tenant-scoped unique index where uniqueness is per tenant, for example
   `[["tenantId", "email"]]`).
5. In `option` mode, clients must call `POST /api/tenant/select` after login; tokens minted at login
   carry no tenant.

## Tests

`npm test` covers the rule preprocessor, the tenant decision, `deleteTables` generation and the
generated output, with a golden scenario for each mode and for the cleanup tables.
`npm run test:e2e` proves both modes against a real Postgres — option mode through login → list →
select → scoped CRUD → account deletion, and preSelect mode with no auth module at all.
