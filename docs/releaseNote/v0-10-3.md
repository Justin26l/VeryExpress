# v0.10.3

## Unique constraint names include the table

PostgreSQL requires a constraint name to be unique inside a schema, not inside one table. The
generated `@Unique` name carried the columns only:

```ts
@Unique('unique_tenantId_code', ['tenantId', 'code'])
```

Two documents declaring `"uniqueIndex": [["tenantId", "code"]]` therefore emitted the same
constraint name, and the app failed at startup with:

```
relation "unique_tenantId_code" already exists
```

The name now includes the table:

```ts
@Entity("branch")
@Unique('unique_branch_tenantId_code', ['tenantId', 'code'])
```

| Document | Table | Constraint |
| --- | --- | --- |
| `Branch` | `branch` | `unique_branch_tenantId_code` |
| `AdminRole` | `adminrole` | `unique_adminrole_tenantId_code` |

The table name is the one the entity already carries (`documentName.toLowerCase()`), so the
constraint stays stable when a document is renamed.

## Migration

1. Re-run the generator.
2. A fresh database needs nothing else.
3. An existing database keeps the old constraint names. TypeORM compares constraints by name, so
   `SQL_SYNCHRONIZE=true` drops and recreates them on the next start. Without synchronize, rename
   them by hand:

```sql
ALTER TABLE "branch" RENAME CONSTRAINT "unique_tenantId_code" TO "unique_branch_tenantId_code";
```

A database that already failed to start holds no table for the second document; create the table
after the rename.

## Tests

`npm test` covers the new names across the golden scenarios. The collision itself is checked against
PostgreSQL: two generated entities that declare the same column set synchronize into one schema, and
a pair of hand-built entities with a shared constraint name reproduces the original error.
