# v0.8.4

## Account deletion (tombstone)

Generated apps now get self-service account deletion: `POST /api/auth/delete-account` and a
`/delete_account` page, on by default.

The account is **soft-deleted**, not erased. The row survives so business tables can keep their
required foreign keys — a hard delete would orphan every `Job`, `ChatMessage` and `UserReport`
pointing at it — while credentials and personal data are removed.

| Step | Effect |
|---|---|
| Clear credentials | `UserAuthProfiles`, `UserRole`, `Session` rows for the user are hard-deleted |
| Tombstone last | `deleted: true`, `email` → NULL, `name` → `"Deleted user"`, `locale` / `profileErrors` → NULL, `active` → false |

Credentials are removed **before** the tombstone on purpose. Tombstoning first would leave the OAuth
path able to resolve the account through `provider` / `oauthId`, i.e. a deleted user could log back
into their own tombstone. Marker last also means a mid-flight failure leaves a live account that can
simply be retried.

`email` becomes `NULL`, never `""`: `User` declares a unique index on it, so a second deletion would
collide on the empty string, and the same address must be able to register a fresh account
immediately.

Deletion is idempotent — a repeat call changes nothing.

## Soft delete: `x-vexData: "softDelete"`

Soft delete is a general, opt-in schema feature, not a hard-coded user concept. Tag one boolean
property:

```jsonc
"deleted": { "type": "boolean", "default": false, "x-vexData": "softDelete" }
// and list it in the root "required" array
```

- **Not client-writable.** The marker is omitted from the generated request body (`PayloadUser`), so
  a client cannot soft-delete, resurrect or pre-tombstone a row through the CRUD API.
- **Hidden by default.** The adapters add `marker IS NOT TRUE` (`$ne: true` on Mongo) to every read
  and write filter. No call-site changes.
- **No new columns.** `softDelete(id, data?)` writes the marker through the normal update-phase
  machinery, so `updatedAt` / `updatedBy` record who deleted the row and when. There is no
  `deletedAt` / `deletedBy`.
- **Required + defaulted.** The marker must be `boolean`, `default: false` and `required`, producing
  `boolean NOT NULL DEFAULT false`. A nullable marker would make the hide-filter drop every row
  written before the column existed.

Internal callers use dedicated repository methods, never a filter key:

```ts
softDelete(id, data?)                    // write the marker + redaction in one update
findOneWithDeleted(filter, join, select) // skip ONLY the soft-delete term; ownership still applies
```

A soft-delete key inside `Filter<T>` was rejected deliberately: `Filter` is the shape of every HTTP
`filter` body, so it would have been a client-side bypass.

The hide term is **not** applied to relation loading — which is why the marker is a plain column and
not TypeORM's `@DeleteDateColumn`, whose relation-nulling would break retained conversations
rendering "Deleted user".

## Tokens of deleted accounts are rejected

`Authentication.middleware` verified the JWT signature and nothing else, so a deleted user's
unexpired access token kept working for the rest of its lifetime. A generated `AccountStateGuard`
now closes that gap.

It reads the marker **value** rather than relying on the row being hidden, so the answer holds even
under `app.showSoftDeleted`, where a visibility-based check would call every tombstone alive. It
treats a missing marker as live (`!== true`), matching the adapters.

Every other auth path was already fail-closed: refresh and the OAuth exchange look the user up
through a soft-filtered read, local login compares an email that is now NULL, and the OAuth callback
cannot re-bind because the profile rows are gone.

## Config

```jsonc
{
  "app":  { "showSoftDeleted": false },
  "auth": { "deleteAccount": true }
}
```

- `auth.deleteAccount` — **default true** (opt-out). Also requires auth to be enabled: a deletion
  endpoint that cannot authenticate a caller could only delete the wrong account. When false, no
  endpoint, no service, no page.
- `app.showSoftDeleted` — **default false**. Lifts the adapter filter app-wide, making tombstones
  visible and writable again. It warns on every generation run, because it is a blunt instrument: it
  applies to every entity, including ones added later.

Both are read with `??`, so an explicit `false` is never swallowed.

## The `/delete_account` page

Served from `LoginUI` rather than as a static file — `express.static("public")` would expose
`public/delete_account.html` at `/delete_account.html`, not at the route a store listing points at.
Linked from `/`.

`LoginUIConfig.deleteAccount` is optional and defaults to true, because an app's `server.ts` is
generated once and is not overwritten on later runs; a required field would stop such a project from
compiling.

The client clears its stored tokens on success — the account is gone the moment the tombstone is
written, so keeping a token the server now rejects would only produce confusing 401s.

## Behaviour changes

- **Every authenticated request costs one extra indexed read** of the identity row when the identity
  document is soft-deletable. Projects with no soft-delete marker are unaffected — the guard is
  emitted as a no-op there.
- **A request carrying a soft-delete marker is rejected with `400 Invalid Request Body`**, matching
  the existing `throw-on-extras` contract for other server-managed fields.

## After upgrading

Re-run the generator. Then:

1. **Add the column.** `useUserSchema` apps get `User.deleted` merged in automatically.
   `SQL_SYNCHRONIZE=true` covers development; production needs
   `ALTER TABLE "user" ADD COLUMN "deleted" boolean NOT NULL DEFAULT false`.
2. **Check `allowOverwrite: false`.** An app that pinned `UserModel.gen.ts` / `User.gen.ts` must add
   the column by hand, or clear those `.vex/meta.json` entries, or the SQL column will not exist.
3. **Business rows and uploaded objects are the app's job.** This release covers the identity domain
   only. Third-party identities too: vex cannot delete a Firebase account — capture the provider uid
   *before* calling the service.
4. **To disable it entirely:** `"auth": { "deleteAccount": false }`.
