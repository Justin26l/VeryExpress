# v0.8.5

## Breaking: the identity key is renamed, and now enforced

`UserAuthProfiles.oauthId` is **`providerUserId`**, and `(provider, providerUserId)` is a **composite
unique index**. The value never changed — it is the subject within `provider`'s namespace — but the old
name claimed a protocol the field does not require, and nothing stopped two rows claiming one identity.

Re-run the generator (migration `v0.8.5` rewrites the schema, and any `uniqueIndex` entry naming the old
field), then migrate the database:

```sql
ALTER TABLE "userauthprofiles" RENAME COLUMN "oauthId" TO "providerUserId";
ALTER TABLE "userauthprofiles" ADD CONSTRAINT "unique_provider_providerUserId"
    UNIQUE ("provider", "providerUserId");
```

Look for existing duplicates before adding the constraint:

```sql
SELECT provider, "providerUserId", COUNT(*) FROM "userauthprofiles"
GROUP BY 1,2 HAVING COUNT(*) > 1;
```

`SQL_SYNCHRONIZE=true` covers development. App code that reads `oauthId` must be updated.

## New: Firebase as a sign-in option

`auth.firebase: true` generates `POST /api/auth/firebase` and a button on the generated `/login` page.
The endpoint takes a Firebase ID token and answers with the vex token pair:

```
POST /api/auth/firebase   { "idToken": "<Firebase ID token>" }
200  { "result": { accessToken, accessTokenIndex, refreshToken, refreshTokenIndex, isNewUser } }
503  no usable service account        401  invalid or expired token
400  the sign-in has no upstream IdP  409  the sign-in carries no email
```

The identity written is the **upstream** IdP's — `("google", <Google sub>)` for a Google sign-in, the
same pair `passport-google-oauth20` writes, so both doors resolve to one `User` row.

```jsonc
"auth": { "firebase": true }
```

That boolean is the only switch. Everything else is environment. Four required values, under the names a
deployment already has; two variables earlier drafts carried are gone because nothing reads them
(`FIREBASE_APP_ID` — Firebase Auth takes no appId — and a file-path alternative to the service account).

| Variable | Used by |
|---|---|
| `FIREBASE_SERVICE_ACCOUNT_JSON` | server — `firebase-admin` |
| `FIREBASE_WEB_API_KEY`, `FIREBASE_WEB_AUTH_DOMAIN`, `FIREBASE_WEB_PROJECT_ID` | login page — public, by design |
| `FIREBASE_PROVIDERS` | optional; which buttons `/login` renders; default `google` |

Design record, including the identity rules and the reasons behind them:
[`docs/plan/spec-firebase-auth.md`](../plan/spec-firebase-auth.md).

## Also fixed

- **A project with `localAuth: false` and any other sign-in path generated a controller that did not
  compile** — `exchangeToken` / `refreshToken` call `this.userRepo`, which was only emitted when
  `localAuth` was on. The getter is now emitted whenever auth is enabled. Reachable before this release
  with `oauthProviders` alone; the Firebase-only configuration is the same shape.

## After upgrading

1. **`npm install`** — `firebase-admin` is a dependency of the generated app (the browser SDK is loaded
   from gstatic by the login page, so the `firebase` package is not needed).
2. **Re-run `vex`.**
3. **Run the SQL above** if your identity table is older than this release.
4. **Set the environment** — the service account, plus the three public values from one *Web* app
   registration in the same Firebase project. Paste the downloaded key file into
   `FIREBASE_SERVICE_ACCOUNT_JSON` as-is: its fields are snake_case (`project_id`, `private_key`,
   `client_email`) and that is what the loader expects.
5. **Turn it on** with `"auth": { "firebase": true }`, then re-run `vex`.
6. **Open `/login`.** The button posts to `/api/auth/firebase`; a failed sign-in names the server-side
   configuration problem it can see (missing variables, an unstartable provider name).

Notes:

- The login page loads the **modular** Firebase SDK as ES modules from gstatic (pinned version), the
  same way the app's own web sign-in does, and preloads it on page load. That needs `www.gstatic.com` in
  `script-src`, plus `connect-src` for the token endpoints and `frame-src` for the project's auth domain
  — the generated page sets all three itself, so an app-wide `helmet` CSP does not have to change.
- The glue is **inlined into the generated page**, not served from `public/js/`. `public/**` is a
  copy-once template, and an earlier draft of this feature put `public/js/firebaseauth.js` there — so a
  project that ran that draft keeps a compat-era file while its page moved on, and the page fails with
  `Firebase sign-in is not configured: window.undefined is missing`. **Delete
  `public/js/firebaseauth.js`** from any project generated from that draft; nothing references it any
  more. (Same for a stale `/js/firebase/*` route, if you carried one.)
- The login page overrides `Cross-Origin-Opener-Policy` to `same-origin-allow-popups`. helmet's default
  (`same-origin`) nulls `window.opener` inside a cross-origin popup, which is the channel the Firebase
  handler reports on, and the SDK then reports **`auth/popup-closed-by-user`** — a message that points at
  the user and the network, never at the header that actually caused it. If you proxy or re-render the
  login page yourself, keep this header.
- `LoginUI.gen.ts` and `FirebaseAuthUI.gen.ts` are regenerated even when `auth.firebase` is false; the
  wiring module exports `undefined` and the page renders no Firebase button.
