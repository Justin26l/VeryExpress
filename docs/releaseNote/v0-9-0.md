# v0.9.0

## Binary fields: `x-format: "Binary"`

A property can now carry a binary payload. Declare it as a string with the `Binary` format:

```jsonc
"data": { "type": "string", "x-format": "Binary", "description": "base64-encoded bytes" }
```

| Layer | Value |
| --- | --- |
| SQL column | `bytea` |
| Entity property | `string` |
| API request / response | base64 string |

A TypeORM transformer converts `string → Buffer` on write and `Buffer → base64 string` on read, so
clients never see a `Buffer` and every generated type stays JSON-safe:

```ts
@Column({type: "bytea", nullable: false,
    transformer: {
        to: (v: string | null) => (v == null ? v : Buffer.from(v, "base64")),
        from: (v: Buffer | null) => (v == null ? v : v.toString("base64"))
    }})
data!: string;
```

`type` must be `string`; any other type fails generation. In mongo mode the column is a plain
`String` holding the same base64 text. The transformer does not validate base64 — `Buffer.from`
ignores invalid characters — and `maxLength` has no effect on a binary column.

Re-run the generator, then migrate the table. `SQL_SYNCHRONIZE=true` covers development; otherwise:

```sql
ALTER TABLE "asset" ADD COLUMN "data" bytea;
```

## SQL target is PostgreSQL

The generated SQL app connects with a fixed `postgres` driver and depends on `pg` only. There is no
MySQL or SQLite path, so binary columns are always `bytea`. A MySQL target would need a dialect layer
between the schema and the entity generator; `blob` is not emitted today.
