# v0.10.1

## Transaction entry owned by the DB layer

Business code can run several writes in one transaction without touching the TypeORM manager:

```ts
await vexDb.transaction(async (tx) => {
    const orderRepo = tx.getRepository(OrderEntity);
    await orderRepo.create({ ... });
});
```

- `tx` only exposes `getRepository`; the manager and the data source are not reachable.
- Returned repositories are the normal adapters, so isolation, audit stamping and fail-closed
  checks behave exactly as they do outside a transaction.
- Throwing inside the callback rolls the whole transaction back.
- Nested calls throw `nested transaction is not supported` instead of silently opening a second
  transaction.
- The mongo target throws `VexDb.transaction is only available for the SQL target`.

`vexDb.dataSource` is now private. `VexDbConnector` is the only place that reads it.

### `VexRepository.save`

`save` is the upsert-shaped write the transaction callback exposes:

| Payload | Behaviour |
| --- | --- |
| no `_id` | insert, with the normal create-phase audit fields and isolation stamping |
| with `_id` | update that row; a row outside the caller's isolation is a `404` |

Isolation fields are stripped before the write, so `save` cannot move a row to another tenant or
owner. Both adapters implement it.

## `tenant.scope`

The tenant middleware applies to every route by default. A deployment whose browser-facing paths
cannot send the tenant header narrows it:

```jsonc
"tenant": {
    "enable": true,
    "IsolationMode": "preSelect",
    "scope": ["/api"]
}
```

- Prefix match on `req.path`, boundary-aware: `/api` matches `/api/...` but not `/apix`.
- Omitted → every route (the previous behaviour).
- An entry must start with `/`; an empty list is rejected at generation time.
- `/hello` stays exempt.

In `preSelect`, `scope` must cover the auth routes used by the client (normally `/api` or
`/api/auth`): login reads the tenant captured by the middleware.

Tenant existence is not checked by the middleware. It validates the UUID only; whether the tenant
exists, is disabled or was deleted is the application's lookup, whose normal answer is `404`.

## Migration

1. Re-run the generator.
2. Replace any `vexDb.dataSource.transaction(async (manager) => ...)` with
   `vexDb.transaction(async (tx) => ...)`; `manager.getRepository(...)` becomes
   `tx.getRepository(...)`.
3. `dataSource` is private, so direct reads no longer compile. This is intended: the transaction
   handle is the supported boundary.
4. `tenant` config without `scope` keeps the previous routing behaviour.

## Tests

`npm test` covers the generated shapes and the unchanged default. `npm run test:e2e` runs a probe
inside a generated app against Postgres: tenant stamping inside a transaction, fail-closed `403`
without a tenant, rollback of every write on throw, and the nested-call rejection.
