# v0.8.0

## Auto-written audit / ownership fields

The DB layer now fills `createdBy` / `createdAt` / `updatedBy` / `updatedAt` itself, from the schema
declaration. Before this release those columns existed in every generated entity but nothing ever wrote
them — a `findOne({ _id, createdBy: user._id })` ownership check could never match, which surfaced as
silent `404`s in downstream apps.

Declare a field with one of six reserved `default` keywords:

```jsonc
"createdAt": { "type": "string",  "x-format": "Timestamp", "default": "onCreateTimestamp" },
"createdBy": { "type": "string",  "x-format": "UUID",      "default": "onCreateUserId" },
"updatedAt": { "type": "string",  "x-format": "Timestamp", "default": "onUpdateTimestamp" },
"updatedBy": { "type": "string",  "x-format": "UUID",      "default": "onUpdateUserId" }
```

- `onCreate*` is written on `create`; `onUpdate*` on `update` / `replace`. The opposite phase **strips**
  the field without writing it, so `createdAt` / `createdBy` can never be overwritten by a PATCH.
- Client-supplied values for these fields are always discarded — a caller cannot forge `createdBy`.
- No authenticated context (public / internal call): timestamps are still written, owner fields are left
  untouched. Never `"undefined"`, never a thrown error.
- Both targets implement it (TypeORM and Mongoose); no SQL `DEFAULT` / `ON UPDATE` is generated, so the
  adapter stays the single source of truth.

## Identity source: `x-vexData: "userId"`

Exactly one field across all schemas is tagged as the identity source (the template tags `User._id`):

```jsonc
"_id": { "type": "string", "x-format": "PrimaryUUID", "x-vexData": "userId", "index": true }
```

`useUserSchema` apps get the tag added automatically on the first run after upgrading; other apps declare
it themselves. `onCreateUserId` / `onUpdateUserId` require it and generation fails with a clear message
when it is missing, duplicated, or when the column types of the two sides disagree.

## Token claims

Access tokens now carry `vexUserId` (the tagged field's value) and `vexRole`. Refresh tokens carry
`vexUserId` only — roles are a signing-time snapshot and the refresh endpoint re-reads the user anyway.
`POST /auth/refresh` resolves the user by the tagged field; `payload._id` is still accepted, so refresh
tokens issued before the upgrade keep working. The public `profile` object is unchanged.

## New `x-format: "Timestamp"`

Datetime columns (`timestamptz` on PostgreSQL). Distinct from `UnixTimestamp`, which stays integer epoch
seconds. Generated entities convert the driver's `Date` back to an ISO-8601 string, so the API and the
generated interfaces keep their `string` contract.

## Request body no longer accepts server-managed fields

The interface generator now emits a request-body alias per document:

```ts
export type CreateJob = Omit<Job, "createdAt" | "createdBy" | "updatedAt" | "updatedBy" | "_id">;
```

Controllers take `Create{Doc}` / `Partial<Create{Doc}>`, so the OpenAPI request schema only lists fields a
client may send, and `_id` is dropped from the input as well (unless `app.allowApiCreateUpdate_id` is
true). The response schema is unchanged — clients still read `createdAt` / `createdBy`.

The omission follows the **declaration**, not the field name: audit fields are recognised by their
reserved `default` keyword, the primary key by `x-format: Primary` / `PrimaryUUID`.

**Behaviour change:** the generated tsoa config is `noImplicitAdditionalProperties: "throw-on-extras"`, so
a request that still sends one of these fields is now rejected with `400 Invalid Request Body` instead of
being silently stripped. Any client that GETs a row and PATCHes the whole object back must remove
`_id` and the audit fields first.

## Breaking changes

- No schema is broken: a field without a reserved keyword keeps its exact previous behaviour, and a
  literal `default` (`"default": true`, …) still means what it always did.
- **Behaviour change for clients**: a request that sends a server-managed field (`_id`, or any field
  declared with a reserved keyword) is now rejected with `400` instead of being silently stripped.
- Rows created before the upgrade keep `createdBy = NULL`; nothing is backfilled.

## After upgrading

Re-run the generator. Consequences per app:

1. Entities pick up the audit columns (all `nullable`), plus a transformer on `x-format: "Timestamp"` columns.
2. Audit fields start being written from the next write onward. **Existing rows are not backfilled** — an
   app that requires ownership on legacy rows has to migrate its own data.
3. Applications with a custom ownership check reading `createdBy` will start working once rows are written
   again; rows created before the upgrade still have `NULL` there.
4. `x-format` values stay capitalized (`Primary`, `PrimaryUUID`, `UUID`, `UnixTimestamp`) with `Timestamp`
   added — schemas written against the lowercase prototype variant must be corrected.
5. Clients that PATCH a whole row they previously GET'd must drop `_id` and the audit fields, otherwise
   the request now fails with `400 Invalid Request Body`.
